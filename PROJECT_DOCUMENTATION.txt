CampusERP Vision
Complete Technical Documentation
================================

Document Purpose
================
This document provides a complete technical and operational description of the
CampusERP Vision project. It is intended to serve as a master reference for:

- project understanding
- technical handover
- viva / demonstration support
- deployment and setup
- maintenance and troubleshooting
- future scaling discussions
- architecture review
- feature planning

The goal of this document is not only to describe what the project is, but
also to explain how the project works internally, what technologies it depends
on, how each module behaves, where the current design is strong, where it is
limited, and what should be done next if the system grows into a larger
production-grade college ERP platform.


1. Executive Summary
====================
CampusERP Vision is a web-based college ERP system implemented in Python using
Flask. The application combines student profile management, role-based login,
facial-recognition attendance, academic record management, bulk marks import,
fee tracking, notices, lecture schedule viewing, and a separate student portal
inside a single browser-driven workflow.

At a functional level, the project solves the following institutional needs:

- maintaining a central student registry
- associating each student with an enrollment identity and face profile
- recording daily attendance using facial recognition
- providing admin control over academic data and fee records
- allowing students to log in and view only their own information
- supporting bulk marks import for departmental or class-wide updates

At a technical level, the project uses:

- Flask for request routing and template rendering
- SQLite as the local relational database
- face-recognition for biometric matching
- OpenCV, Pillow, and NumPy for image handling
- openpyxl and csv parsing for marksheet upload
- server-rendered Jinja templates for the UI
- custom JavaScript for webcam access and attendance submission

This system is currently best suited for:

- project demos
- academic submissions
- department-level pilots
- internal college automation on a local or small server

The system is not yet optimized for:

- very large multi-campus deployments
- heavy concurrent traffic
- high-scale face search workloads
- internet-facing enterprise production without hardening


2. Project Vision and Problem Statement
=======================================
Traditional attendance and college administration methods are often fragmented.
Attendance may be maintained manually in registers, marks may exist in
spreadsheets owned by separate faculty members, and fee information may be
tracked in isolated systems or even paper records. Such fragmentation creates:

- duplication of effort
- delays in status visibility
- inconsistent records
- weak auditability
- higher risk of manual error
- poor student self-service

CampusERP Vision is designed to unify several academic administration concerns
into a single platform. Instead of separate disconnected tools, the project
brings together:

- student master data
- biometric attendance
- academic scoring
- fee tracking
- schedule awareness
- role-specific access

The added differentiator in this project is facial recognition for attendance.
Instead of requiring RFID cards, fingerprints, or manual signature-based
presence marking, the project allows attendance capture through a browser camera
and a pre-enrolled face profile.

===========================
The primary objectives are:

1. Create a centralized student information system.

Secondary objectives include:

- giving administrators quick operational dashboards

- reducing the effort required to maintain repeated semester records

8. High-Level System Architecture
=================================
The system follows a monolithic server-rendered web application pattern.

Architecture layers:

1. Presentation Layer
   HTML templates rendered by Flask using Jinja.

2. Interaction Layer
   Vanilla JavaScript for browser camera integration and API submission.

3. Application Layer
   Flask route functions, form handlers, validation logic, dashboard queries,
   authentication logic, and feature workflows.

4. AI / Processing Layer
   Face detection and encoding comparison using the face-recognition library.

5. Data Layer
   SQLite for student data, attendance, academics, fees, schedules, notices,
   and admin accounts.

Request flow example:

- Browser opens /attendance
- Admin starts webcam
- JavaScript captures a frame and sends it to /api/attendance/recognize
- Flask decodes the image
- face-recognition extracts the face embedding
- system compares the embedding against saved student encodings
- best match is selected if distance <= threshold
- attendance is inserted into SQLite
- result is returned as JSON
- page updates with success or failure message

12. Authentication and Session Handling
=======================================
12.1 Admin Login
Admin users sign in with:

- role = admin
- username
- password

The password is checked against a hashed password stored in admin_users.

12.2 Student Login
Students sign in with:

- role = student
- enrollment number
- portal password

Important behavior:

- enrollment number comparison is case-insensitive
- portal password is verified against a stored password hash
- if the student record does not exist, access fails
- once authenticated, the session stores:
  role, user_id, display_name, login_id

12.3 Session Security Model
The system uses Flask session storage to keep track of the current logged-in
identity. Routes are protected by decorators:

- admin_required
- student_required

This means:

- admin routes reject non-admin users
- student routes reject non-student users
- role separation is enforced in route access

14. Face Image and Encoding Pipeline
====================================
14.1 Face Image Storage
The project stores the student image path in the database and saves the actual
image file inside:

- static/uploads/

14.2 Image Processing
Before saving:

- image is converted to RGB
- image is resized / thumbnail-limited for storage efficiency

14.3 Face Detection
The face_recognition.face_locations() function identifies face positions.
The current implementation uses the HOG model.

14.4 Encoding Creation
Once one valid face is found, face_recognition.face_encodings() generates a
feature vector for the face. This vector represents the biometric identity.

14.5 Encoding Storage
The encoding vector is serialized into JSON text and stored in the
students.face_encoding field.

14.6 Validation Rules
The system deliberately rejects:

- images with no face
- images with more than one face

This improves matching integrity.


15. Attendance Recognition Workflow
===================================
The attendance workflow is one of the project’s main AI-enabled capabilities.

15.1 Frontend Attendance Flow
- Admin opens attendance page.
- Browser starts camera.
- Admin captures a frame.
- JavaScript sends the frame as a data URL to the backend.

15.2 Backend Attendance Flow
- backend receives JSON payload
- backend decodes image
- backend extracts a face encoding
- backend loads all stored student encodings
- backend computes vector distances
- closest match is selected
- if best distance <= threshold, student is recognized
- attendance is inserted for the current date

15.3 Recognition Threshold
Current configured threshold:

- 0.47

15.4 Duplicate Attendance Protection
Attendance records are unique per student per date. If the student has already
been marked present, the system returns success with an already_marked flag
instead of creating a second row.

15.5 Confidence
The system calculates a confidence-like percentage derived from face distance
and stores that value with the attendance log.

19. Bulk Result Upload Workflow
===============================
Bulk import is the large-scale academic processing feature in the system.

Supported formats:

- .xlsx
- .csv

Required columns:

- enrollment_no
- assessment_name
- course_code
- course_title
- score
- max_score

Header flexibility:
The backend normalizes several alternative header names into canonical fields.
This reduces operational friction when administrators upload real spreadsheets.

Examples of accepted variants:

- enrollment, enrollment_number, student_code
- assessment, exam_name, test_name
- subject_code, paper_code
- course_name, subject_name
- marks, obtained_marks
- max_marks, total_marks, out_of

Import flow:

1. Admin uploads file.
2. System detects file type.
3. System parses rows.
4. Blank rows are skipped.
5. Required columns are validated.
6. Numeric score fields are validated.
7. Enrollment numbers are normalized.
8. Student records are matched.
9. Valid rows are deduplicated in-memory by:
   student + assessment + course code
10. Results are upserted into the database.
11. Success feedback includes number of rows processed and missing students.

This design is important because it makes large departmental updates feasible.

27. Current Performance Profile
===============================
27.1 What Performs Well
- local route rendering is fast
- SQLite lookups are fast for small datasets
- dashboards are efficient for demo-size data
- bulk result import is efficient for moderate spreadsheet sizes
- image upload sizes are constrained to manageable dimensions

27.2 What Becomes Expensive
- attendance face comparison scales linearly with student count
- repeated aggregate dashboard queries may grow slower as data volume grows
- SQLite write concurrency is limited
- image decoding and encoding happen in request-time execution

27.3 Why the Face Pipeline Is the Main Scale Bottleneck
The current attendance match logic:

- loads all student encodings
- computes face distance against every stored student
- chooses the minimum distance

This means performance degrades as the student registry grows. For a small
project this is acceptable. For a large institution, a more advanced embedding
search or vector indexing strategy is recommended.


28. Scalability Analysis
========================
If the project grows from a demo to a real institutional system, the following
areas will need redesign or hardening:

28.1 Database
SQLite should be replaced with:

- PostgreSQL
- or MySQL

Reasons:

- stronger concurrent write support
- better scalability
- better operational tooling
- easier backup / replication strategy

28.2 Attendance Recognition
The current synchronous recognition path should evolve into:

- a recognition microservice
- a worker queue model
- or a vector-search based identity matcher

28.3 Caching
Frequent dashboard aggregates can be cached using:

- Redis
- in-memory caching
- precomputed reporting tables

28.4 File Import Processing
Very large mark sheets should move to:

- asynchronous background job processing
- progress tracking
- import history logs
- failure row exports

28.5 Access Control
A larger deployment should include more roles:

- super admin
- academic admin
- faculty
- accounts
- HOD
- student

29. Security Review
===================
Current strengths:

- passwords are hashed
- routes are role-protected
- student route access is restricted by session identity
- no raw password storage
- duplicate attendance prevention exists

Current gaps:

- no CSRF protection layer
- no brute-force protection
- no password complexity enforcement
- no MFA
- no audit event logs
- no file antivirus scan
- no signed upload mechanism
- no HTTPS enforcement in development mode

Production recommendations:

- set a strong secret key via environment variable
- add CSRF protection
- add login throttling
- add password rotation policies
- add audit logging for admin operations
- add secure deployment behind HTTPS
- restrict upload types and content more aggressively
